# Контекст, проверки и документация

## UC-CONT-001

**Когда:** нужно выбрать контекст и место работы; пользователь мог назвать
репозиторий/несколько репозиториев в **сообщении, вызвавшем чтение README**.

**Цель:** без искусственной привязки определить нужные репозитории и владельцев.

**Как:** сначала прочитать исходную задачу и известный контекст; затем короткий
вход главного реестра и обязательные [UC-CONT-002](delivery.md#uc-cont-002) и
[UC-CONT-003](delivery.md#uc-cont-003). **Не сканировать всю таблицу UC.**
Если один/несколько repo явно указаны — сверить точные пути, Git status, ветки,
HEAD и worktree list. Если собственник однозначно следует из [карты][sources] —
использовать его без лишнего вопроса; при нескольких repo отдельно определить
ownership изменений. Если репозиторий необходим, но не определяется, уточнить
одним вопросом: существующий один/несколько, новый или работа без привязки?
Не создавать новый репозиторий без согласованной необходимости. Исследование,
планирование и концептуальная работа могут выполняться вообще без repo.
**Чтение README проекта не доказывает, что задача относится к этому проекту.**
Если repo выбран, открыть только его применимый локальный реестр и документы;
защищать чужие dirty изменения без reset/clean/массового stash. Для task worktree
— [UC-CONT-019](worktrees.md#uc-cont-019).

**Готово:** указан один/несколько владельцев либо явно допустима работа без
репозитория; известны scope и next step, неизвестные ограничения не скрыты.

## UC-CONT-016

**Цель:** получить достаточное доказательство результата без тяжёлой имитации среды.

**Как:** следовать [validation policy](../VALIDATION-POLICY.md), запускать
проверки изменённого поведения. Для документации проверять навигацию/ссылки и
whitespace; для политик — ALLOW/ASK/DENY и границы scope; для кода — нужный suite.
Реальные Docker/Windows/credentials/effect проверки выполнять в целевой среде
по согласованному маршруту. Source test не доказывает успешное внедрение.

**Готово:** evidence различает SOURCE-VERIFIED, LIVE-VERIFIED, OWNER-REPORTED,
MANUAL-PENDING и UNKNOWN; ограничения записаны у владельца результата.

## UC-CONT-017

**Когда:** документы устарели, дублируются, тяжело поддерживаются, не дают
понятной карты модулей/владельцев или смешивают план с live-состоянием.

**Цель:** поддерживать короткую, полезную, понятную документацию с одним
нормативным владельцем для каждого факта (DRY), не заменяя ею исходники.

**Как:** проверить исходную задачу, реальные файлы, связи и существующие owners.
Различать contract, current state, plan и dated evidence. Документировать
неочевидные правила: границы ответственности, разрешения, порядок действий,
принятие решений, побочные эффекты и ограничения. **Даже если детали можно
восстановить из исходников, документация может потребоваться как структура:**
карта компонентов, назначение модулей, зависимости, пути к исходному коду,
тестам и точным контрактам. Давать короткое объяснение **почему и где искать**, а
не дублировать в Markdown каждую функцию, параметр, поле, CLI-команду или
очевидную реализацию. Для сложного кода допустим короткий структурированный
обзор с проверяемыми ссылками; при изменении кода он должен требовать минимум
сопутствующей ручной правки. При необходимости обновить/объединить owner,
поставить alias, отметить historical archive, а не создавать новый документ без
потребности. Предпочитать короткие корректировки. Для новых reusable сценариев
использовать [UC-CONT-024](#uc-cont-024). Для будущих улучшений в любом сопровождаемом
репозитории использовать **один** `docs/BACKLOG-IMPROVEMENTS.md`: перед созданием
найти существующие `FUTURE-*`, `FOLLOW-UP-*`, roadmap/technical debt, перенести
живые задачи и обновить ссылки; исторические планы оставить архивными.
Backlog не заменяет runbook, evidence или точный action plan. Навигацию README/AGENTS менять ровно
настолько, насколько нужно для поиска владельца; проверить ссылки и [UC-CONT-016](#uc-cont-016).

**Готово:** читатель быстро понимает, **что где находится, как это связано и
какие правила не видны в коде**, и по ссылкам достигает точных источников.
Нет самостоятельных копий runtime, API или списка мелких методов, нет ссылок на
старый PAT/GitHub route как действующий; документация поддерживается пропорционально
изменениям проекта.

## UC-CONT-024

**Когда:** возникает повторяемая цель, не охваченная реестром, либо существующий
Use Case больше не ведёт к правильному результату.

**Цель:** создать или поправить **Use Case — самостоятельную повторяемую ситуацию
с проверяемым результатом**, а не заметку о единичной команде, функции или релизе.

**Как:** сначала искать применимый сценарий среди кратких входов главного и
локального реестров. Если UC уже есть — улучшить, а не дублировать; разовые
действия оставить в task/evidence. Выбрать владельца: общее Docker/GitHub/AI
поведение — `UC-CONT-*`, специфика проекта — его локальный `UC-...`.
Описать **Когда, Цель, Как, Готово**, prerequisites, STOP/UNKNOWN, связанные UC,
нормативного владельца/ссылки и статус. Для ориентации в коде дать **краткую
карту ответственности и точные пути/ссылки к исходникам**, если она ускоряет
понимание; не копировать тривиальные сведения о каждой функции и параметре.
Присвоить стабильный ID, зарегистрировать Situation/Result без требования читать
все UC; локальный registry включить в центральный каталог. При переносе UC
сохранить старый якорь с redirect. Проверить DRY по [UC-CONT-017](#uc-cont-017),
адреса/ссылки, владельцев и нужные тесты. Не создавать Git repo только ради UC.

**Готово:** сценарий имеет единственный точный owner и доступен из правильного
реестра; условие применения, результат, кодовые ссылки, status и запреты
проверены, старые ссылки продолжают работать.
