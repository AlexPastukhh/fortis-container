# AI integrations

## Shared execution model

There is one shared Fortis Repo Docker container for these client paths; a client connection or a Desktop Commander child process is not a new container.

- ChatGPT Repo1 uses the Windows Tunnel / Repo1 worker chain.
- ChatGPT Repo2 uses the Windows Tunnel / Repo2 worker chain.
- Qwen Studio uses a Windows-side MCP proxy and a container-side STDIO gateway.
- Repo1, Repo2 and the Qwen gateway target the existing Fortis Repo container and shared workspace. The Qwen path uses `docker exec`, not `docker run` or a new container.

The Tunnel runbook describes Repo1 and Repo2 as separate Windows profiles with one shared Guard policy. Their latest reconnect status is OWNER-REPORTED; this documentation session did not inspect Windows processes.

The current Desktop Commander process and the Qwen gateway run as Linux UID/GID 1000. Both paths use the same workspace tree. Separate per-client container volumes or OS identities are not established by the available evidence; other container processes were not exhaustively enumerated.

## ChatGPT / Repo1 / Repo2

The documented route is ChatGPT account → Windows Tunnel Client / profile-specific Repo worker → existing Fortis Repo container → Desktop Commander MCP.

Source ownership:
- `tunnel`: Repo1/Repo2 workers, Windows launcher chain, shared Guard policy and runtime source map.
- `script-control-center`: Script Catalog/Control Center UI, thin worker adapters, resolver and paired updater.
- Fortis Repo container: separate runtime; it is not built from the Tunnel repository.

The installed legacy wrapper still contains the historical `C:\\Users\\alexa` replacement text, but that exact claim is absent from the current connected schema. Current Repo1/Repo2 workers use the direct Desktop Commander entry point; the bridge is not in their observed process path.

The exact source-to-session mapping is not established by the supplied transcript and proxy log.

## Shared files and concurrent work

ChatGPT Repo1, Repo2 and a Qwen process using this container can access the same workspace according to their tool surface and OS permissions. The pinned six-tool read-only gateway allowlist restricts that particular MCP interface; it is not a separate OS identity or filesystem boundary. The owner-reported full Qwen tool path must be assessed by its actual process permissions, not by the separate six-tool source. Same-UID processes may access files permitted to UID 1000.

No automatic file-level synchronization exists between Docker checkouts and the separate Windows Git clones. The documented Tunnel / Script Center delivery path is Git commits followed by the Windows Preview/Apply workflow.
