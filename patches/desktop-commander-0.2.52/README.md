# Desktop Commander 0.2.52 — Fortis path-guidance patch

**Status: DEPLOYED AND LIVE-VERIFIED 2026-11-04.**

This narrowly corrects the `OS_GUIDANCE` generated by
`dist/utils/system-info.js` for `start_process`.

## Change

- Keep the runtime-discovered mounted-directory list.
- Tell the tool to use those exact container paths.
- Do not guess host-to-container mappings or rewrite paths into `/home`.
- If a host-side path is supplied, require a verified runtime mount mapping;
  otherwise ask for the corresponding container path.
- With no detected mounts, do not recommend a generic Docker remount or
  assume the Docker Installer's `/home/[folder-name]` layout.

`getPathGuidance()` is verified byte-for-byte unchanged. No `server.js`,
`PATH_GUIDANCE`, schema, bridge, or Qwen code is changed.

## Build-stage use

A patch-only Dockerfile derives from the existing
`fortis-repo-mode:dc-0.2.52` image. It applies and tests the patch as root
during image build, then restores runtime user `1000:1000`. It inherits the
base image's ENV, WORKDIR, ENTRYPOINT and CMD.

On the Windows Docker Host, the runner is copied from the active container and
executed as follows:

```powershell
$script = Join-Path $env:TEMP 'fortis-build-path-guidance-candidate.ps1'
docker cp fortis-repo-test:/workspace/repos/fortis-container/patches/desktop-commander-0.2.52/build-candidate.ps1 $script
& $script
```

The runner fails closed unless the reviewed container ID, base image tag/ID
and read-only-root setting still match. It copies this patch directory into a
temporary build context, builds with `--pull=false`, and checks that the
candidate image's default user, command, entrypoint and workdir match the base.
It does not start, stop, restart or replace any container.
